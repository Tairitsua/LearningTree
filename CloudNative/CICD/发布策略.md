# 发布策略

> 治理留痕（2026-09-30）：本文件由原 `CloudNative/Kubernetes/Kubernetes监控.md` 的 `## 发布` 章节迁出（该文件另迁出了 Git 提交规范与网络章节）。

发布和部署不同，一次发布可能包含多次部署。

## 数据库变更

数据库变更新增字段等操作，可以申请强制变更（即无法回滚的升级）。否则想要安全只能代码做两个新旧版本的数据库兼容。

## 发布方式

### A/B测试

在两个犹豫版本中选择一个发布，一般对于前端，让用户使用情况来判断哪种设计更好。

### 金丝雀发布

降低发布风险，逐步将旧版本升级到新版本（流量慢慢切到新版本）。先把新版本发布给一小部分用户/流量（如内部员工、随机小比例用户），观察无异常后再阶梯式放量直至全量；一旦发现问题可立即把流量切回旧版本。

### 灰度发布

在中文语境下通常与金丝雀发布（Canary Release）同义：不做一次性全量切换（非黑即白），而是按流量比例或用户特征（白名单、地域、用户标签等）逐步放量，让系统处于新旧版本并存的"灰色"过渡状态；让部分真实用户先行试用并收集反馈，是常见目的之一。

> 2026-09 核查修正：原文"灰度发布：类似金丝雀发布，但用户参与感更强，让用户参与测试及互动" → 灰度发布与金丝雀发布在业界主流用法中基本同义，均指按流量比例/用户特征逐步放量、风险可控的发布方式；"用户参与感更强、参与测试互动"更接近 Beta/内测的特征，并非两者的标准区别（来源：Martin Fowler《CanaryRelease》——canary release 即 "slowly rolling out the change to a small subset of users"，martinfowler.com/bliki/CanaryRelease.html；另见腾讯云/阿里云开发者社区对灰度发布的通行定义）。若要细分，可把"金丝雀"视为灰度发布的一种典型实现：先以极小流量探测，再阶梯式放量。
